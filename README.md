# YouGile Operations Portal

Веб-приложение для переноса портала управления назначениями из n8n в отдельный сайт и backend.

## Архитектура

```text
apps/
  web/                 React + TypeScript, пользовательский интерфейс
  api/                 Fastify + TypeScript, HTTP API и фоновые задачи
    prisma/             схема PostgreSQL
    src/
      modules/          auth, users, sites, assignments, audit, history, settings
      integrations/     клиент YouGile
      modules/imports/  разбор XLSX-планов, сопоставление и подтверждение
      jobs/              массовые операции и отслеживание прогресса
      routes/            HTTP-маршруты
packages/
  shared/               общие DTO и схемы API (добавлять по мере миграции)
```

Веб-клиент не должен обращаться к YouGile напрямую. Целевая архитектура хранит секреты интеграции только на сервере, проверяет права пользователя и передаёт длительные пакетные операции в очередь. PostgreSQL предназначен для пользователей, сопоставлений площадок и пользователей YouGile, операций, истории и настроек. Redis предусмотрен для очереди фоновых задач и не является источником бизнес-данных.

## Перенос из n8n

В workflow `[PROD] Yougile_new_portal` обнаружены следующие сценарии:

| Сценарий n8n | Модуль приложения |
| --- | --- |
| Загрузка XLSX, сопоставление площадок и пользователей | `imports` + `sites` + предварительный просмотр |
| Подтверждение и назначение инженеров | `assignments` + фоновые задания |
| Снятие инженера с площадок | `assignments` |
| Проверка назначений и расхождений | `audit` |
| Прогресс, журнал запусков и XLSX-загрузки | `jobs` + `history` |
| Шаблон комментария и параметры | `settings` |
| Синхронизация пользователей YouGile | `users` |

Модель `SiteTask` сохраняет ключевые поля таблицы n8n `task` (`id_site`, `Id_site_youg`, `user`, `user_Id`, `address`, `time`, `day`, `What_is_required`, `klaster`, `comment`, `assigned`) и исходную запись в `rawData`. Это позволяет перенести данные без потери полей, которые ещё не описаны в доменной модели.

Раздел «Площадки» получает активные задачи напрямую из YouGile через `GET /api-v2/task-list` и выводит номер площадки, заголовок задачи, количество назначенных инженеров и статус выполнения. По умолчанию используется доступная колонка `951ff78e-1fa5-4334-b34f-288f00609b69`; при необходимости её можно заменить в `.env` параметром `YOUGILE_PLAN_COLUMN_ID`. Список загружается страницами по 1000 записей и кешируется API на 30 секунд. XLSX используется для отбора строк назначения, но сам по себе не изменяет задачи YouGile.

Сценарий «Назначить инженера» начинается с загрузки XLSX-файла с колонками `id_site` и `user`. API автоматически сопоставляет номер площадки и имя инженера с актуальными данными YouGile. В назначение попадут только строки, где найдены и площадка, и ровно один сотрудник с таким именем; неизвестные или неоднозначные имена, отсутствующие площадки, дубликаты и некорректные строки попадают в отдельный список проблем, который можно скачать в XLSX. В настройках можно сохранять отдельные шаблоны комментариев для фильтров, балансеров, байпасов и EHW; выбранный шаблон можно вставить в форму XLSX. Шаблон (до 10 000 символов) поддерживает `${data}` и `${time}` из соответствующих колонок XLSX. Если `day` равен `ночь`, `${data}` становится диапазоном из исходной даты и следующего календарного дня. Предпросмотр показывает готовый текст для каждой строки, и именно этот текст публикуется в чат задачи, в том числе если инженер уже назначен. Ход операции и результат по каждой площадке сохраняются в PostgreSQL.

Раздел «Аудит» показывает последние пять загрузок XLSX с именем файла, временем, количеством строк и статусом. При успешной новой загрузке более старые файлы и содержимое их строк удаляются. Данные уже поставленных в очередь операций хранятся отдельно, поэтому очистка старого XLSX не прерывает назначение. Выбор загрузки открывает в нижнем блоке таблицу всех исходных строк и столбцов файла. До подключения авторизации имя загрузившего отображается как «Локальный оператор».

Сценарий «Снять инженеров» доступен с главного экрана. Источником служит новый XLSX или один из файлов в аудите; снимаются только инженеры, указанные в выбранных строках, и только с площадок из этого же файла. Перед запуском API повторно проверяет текущее состояние задач, показывает оставшихся ответственных и сохраняет их при снятии. Если инженер уже не назначен, строка пропускается без изменения задачи. Операция выполняется в фоне, а результаты и ошибки доступны в интерфейсе.

Сценарий «Проверить работы» принимает новый XLSX или файл из аудита и показывает таблицу с номером площадки и последним сообщением из чата соответствующей задачи YouGile. Строки без сопоставленной задачи и задачи без сообщений остаются в таблице с поясняющим статусом.

Раздел «История» содержит сводные показатели загрузок, успешно обработанных назначений и снятий, график активности за 30/90 дней или всё сохранённое время, статистику по инженерам и пользователям, а также фильтруемый журнал работ с площадкой, инженером, загрузившим и статусом операции. В журнале XLSX хранится только пять последних файлов, поэтому число загрузок в статистике учитывает только доступные файлы. До подключения серверной авторизации действия не привязаны к персональным учётным записям и показываются как «Локальный оператор».

На обзоре карточка «Назначено работ за месяц» показывает число успешных назначений по четырём видам работ: фильтры, балансеры, байпасы и EHW. Вид работы требуется выбрать при назначении по XLSX и сохраняется в данных операции. Успешные назначения, выполненные до сохранения категории, учитываются отдельно как работы без указанного типа.

Порядок переноса:

1. Настроить доступ к YouGile и выполнить импорт существующих таблиц `task`, `users`, `settings`.
2. Перенести вход и роли пользователей; заменить текущий парольный вход на серверную сессию.
3. Расширить импорт XLSX, журнал загрузок и страницу предпросмотра. Запись в YouGile разрешать только отдельным подтверждённым действием.
4. Дополнить фоновые назначения и снятия инженеров повторными попытками и общим журналом операций.
5. Перенести аудит, историю и настройки; сверить результаты с n8n на тестовых данных.
6. Переключить пользователей на сайт и отключить соответствующие n8n-сценарии после приёмки.

Сейчас перенесены список площадок, назначение инженеров по выбранным строкам XLSX с предпросмотром и аудит загрузок XLSX. Снятие и переназначение инженеров, аудит назначений и импорт таблиц n8n ещё не перенесены.

## Запуск

Требуются Node.js 20+, npm и Docker Compose.

```powershell
Copy-Item .env.example .env
npm install
npm run db:generate
npm run db:migrate
docker compose up -d --build
npm run dev --workspace @portal/api
```

Генерация Prisma Client и миграции разделены специально: повторные миграции не перезаписывают загруженный API процессом engine-файл (в частности, на Windows). Docker Compose запускает сайт, PostgreSQL и Redis; API по-прежнему запускается отдельно командой npm. Сайт доступен на `http://localhost:5173`, API — на `http://localhost:4000/api`. Не запускайте одновременно web через `npm run dev`: он займёт порт сайта. Проверьте `YOUGILE_API_URL`, `YOUGILE_API_TOKEN`, `YOUGILE_PLAN_COLUMN_ID` и уникальный `JWT_SECRET`. Значения в `.env.example` предназначены только для локальной разработки.

Для остановки нажмите Ctrl+C в окне API, затем выполните `docker compose stop`. При следующем запуске используйте `docker compose up -d` и снова запустите API командой выше.

## Проверка готовности

- `GET /api/health` проверяет доступность API, PostgreSQL и Redis.
- Перед развертыванием портала для нескольких пользователей необходимо реализовать личные учётные записи, роли и аудит оператора. До этого аудит XLSX указывает загрузившего как «Локальный оператор».
- Массовые операции должны иметь предпросмотр, явное подтверждение, отображение прогресса и запись результата для каждой площадки.
