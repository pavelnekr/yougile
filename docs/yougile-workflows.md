# Рабочие сценарии YouGile

Документ описывает фактическую логику портала в пяти сценариях: точечное назначение инженера, массовое назначение по XLSX, массовое снятие по XLSX, проверка работ и отправка комментария. Основан на текущей реализации `apps/api/src/modules/{assignments,imports,comments,sites}` и `apps/web/src`.

## Общие правила

- **YouGile — источник истины.** Кэш площадок нужен для отображения и выбора, но не является основанием для записи. Перед изменением задачи сервер повторно читает задачу из YouGile и проверяет её актуальное состояние.
- **Личный токен инициатора.** Запросы выполняются от имени сотрудника, который запустил действие; фоновая операция получает автора из `Operation.createdById`. Токен зашифрован в БД и не передаётся в очередь или журнал. Если токен не настроен или не имеет прав, сценарий не сможет работать.
- **Доступ.** Чтение и предпросмотр требуют права чтения `WORK_MANAGEMENT`; запуск изменений требует права записи в это рабочее пространство. Роли портала сами по себе не заменяют право рабочего пространства.
- **Подтверждение перед записью.** Для назначения и комментариев предусмотрен предпросмотр. При старте сервер вновь валидирует входные данные и перечитывает задачи, поэтому предпросмотр в браузере не считается гарантией, что состояние не изменилось.
- **Последовательность и нагрузка.** Фоновая очередь `portal-operations` имеет `concurrency: 1`; площадки внутри операции обрабатываются по порядку `sortOrder`, по одной. Между действиями к YouGile выдерживается 4 секунды. Пока операция или проверка работ идёт, списки плана и АВР обслуживаются из последнего кэша и помечаются `paused`, чтобы не создавать лишние запросы и HTTP 429.
- **Лимит.** Для назначения и снятия аварийный предел — 2 000 площадок/строк за запуск. Для отправки комментариев также 2 000. У XLSX-парсера предел 5 000 строк данных. Проверка работ валидирует выбранные строки без такого лимита операции.
- **Результат и аудит.** Операции записываются в БД с автором, площадками, статусом и результатом по каждой площадке. Итоговые статусы: `SUCCEEDED`, `PARTIAL`, `FAILED`; фоновые старт и результат дополнительно попадают в журнал действий портала. Порядок строк операции сохраняется.

## 1. Точечное назначение инженера

### Назначение сценария

Добавить одного инженера YouGile к одной выбранной площадке (серверный маршрут технически принимает несколько task ID, но для точечного сценария выбирается одна площадка). Существующие ответственные сохраняются.

### Последовательность

1. Интерфейс загружает список сотрудников YouGile (`GET /api/users`) и активные задачи плана (`GET /api/sites/in-plan`). Площадка выбирается по номеру/названию, инженер — из актуального списка пользователей.
2. До запуска вызывается `POST /api/assignments/preview` с `taskIds` и `userId`.
3. Сервер получает актуальных пользователей, активный план и настроенные столбцы АВР, затем для выбранной задачи делает отдельный `GET tasks/{id}`. Проверяется, что задача существует в допустимой колонке, не архивирована и не удалена, а номер площадки совпадает с началом заголовка задачи.
4. Предпросмотр показывает выбранную задачу и текущих ответственных/состояние назначения. Если инженер уже назначен, повторно добавлять его не нужно.
5. После явного подтверждения интерфейс отправляет `POST /api/assignments`. Маршрут повторяет ту же полную проверку, создаёт `Operation` типа `ASSIGN` и строку `OperationItem`, фиксирует автора и снимок `beforeData`, затем ставит `assign-engineer` в очередь. Успешный ответ — `202` с `operationId`.
6. Воркер, используя личный токен автора, заново перечитывает задачу и проверяет план/номер площадки. Если инженер ещё не назначен, формирует новый список `assigned` как объединение текущих ID и выбранного ID, затем обновляет задачу через `PUT tasks/{id}`. Другие ответственные не удаляются.
7. При HTTP 400 запрос назначения повторяется один раз после паузы 4 секунды. При HTTP 429 для назначения включено ожидание 60 секунд и повтор, максимум 10 повторов. Между записью и следующим действием выдерживается 4 секунды.
8. Интерфейс опрашивает `GET /api/operations/:id`, отображает прогресс и завершённый результат. Ошибка одной площадки видна в её строке; итог может быть частичным.

### Необязательное сообщение о назначении

Если включено уведомление о точечном назначении и имя инженера известно, после назначения в чат задачи отправляется сообщение `**{имя}**, возьми в работу, пожалуйста`. Если инженер уже был назначен, сама запись назначения пропускается, но уведомление всё ещё может быть отправлено. Сбой отправки сообщения отмечает площадку как неуспешную, даже если назначение уже успело пройти; уже сделанное изменение не откатывается.

### Проверки и ограничения

- Инженер должен присутствовать среди пользователей YouGile, доступных личному токену.
- Задача должна находиться в активном плане или в настроенном столбце АВР. Архивные/удалённые задачи и несоответствие номера отклоняются.
- Повторно выбранные задачи и неверные UUID не принимаются.
- Очередь не выполняет автоматическую отмену или откат уже применённой записи.
- `GET /api/operations/:id` показывает статус, числа и строки результата; список активных операций можно восстановить после перезагрузки страницы.

## 2. Массовое назначение инженеров по XLSX

### Входной файл и первичный разбор

1. Оператор загружает `.xlsx` через `POST /api/imports/preview`. Используется первый лист. Обязательны заголовки площадки (`id_site`, `site_id`, «номер площадки» или «код площадки») и инженера (`user`, `engineer`, «инженер» или «ответственный»); адрес необязателен. Заголовки нормализуются без учёта регистра, пробелов и знаков-разделителей.
2. Пустые строки пропускаются. Исходные значения колонок сохраняются в `rawData`; номера строк XLSX остаются привязаны к строкам импорта. Поддерживается максимум 5 000 строк данных.
3. API сопоставляет строки с актуальными задачами плана и пользователями YouGile, выставляет статусы строк: `READY`, `SITE_NOT_FOUND`, `ENGINEER_NOT_FOUND`, `INVALID_ROW`, `DUPLICATE_SITE`. Имена инженеров нормализуются общей функцией (включая перестановку слов и `ё` → `е`). Создаётся `ImportBatch` со статусом `PREVIEW`; хранятся пять последних загрузок.
4. Оператор выбирает только подходящие строки. Ошибочные строки можно изучить/выгрузить отдельно; одну и ту же площадку нельзя назначить дважды в рамках одного выбранного запуска.

### Предпросмотр и подтверждение

1. `POST /api/imports/:id/assignment-preview` получает номера строк, тип работ и текст шаблона комментария.
2. API проверяет, что батч существует и ещё в статусе `PREVIEW`; все строки относятся к нему и имеют `READY`; инженер существует и его нормализованное имя совпадает; площадка остаётся в активном плане. Затем повторно считывает задачу и назначения из YouGile.
3. Шаблон рендерится для каждой строки по сохранённым исходным колонкам. Переменные `${data}` и `${time}` берутся из `rawData`. Столбец `klaster` обрабатывается отдельно. Предпросмотр показывает площадку, адрес, инженера, текущих ответственных, уже назначенные совпадения и формируемый комментарий.
4. После проверки оператор подтверждает запуск. `POST /api/imports/:id/assign` заново готовит строки и предпросмотр. Транзакция переводит батч `PREVIEW → ASSIGNING` и создаёт операцию с автором и упорядоченными элементами. Повторный конкурентный запуск того же батча не проходит.
5. Очередь получает `assign-engineer`; ответ `202` содержит `operationId`. Если очередь не приняла задачу, операция помечается `FAILED`, батч возвращается в `PREVIEW`.

### Действия по каждой площадке

Воркер обрабатывает площадки строго по порядку XLSX. Для каждой площадки он заново читает задачу и убеждается, что задача и номер площадки всё ещё соответствуют плану. Затем:

- если заданный инженер отсутствует в назначениях, добавляет его, сохраняя остальных;
- если инженер уже назначен, не меняет список назначенных;
- если задан комментарий, отправляет отрендеренный текст в чат задачи;
- если заполнен `klaster`, дополнительно отправляет в чат `Обрати внимание! Кластер: {площадка}-{кластер}` в текстовом и HTML-представлении.

После каждой успешной записи/отправки применяется 4-секундная пауза. Для назначения включён повтор на HTTP 429 (60 секунд, максимум 10 повторов); на HTTP 400 назначение повторяется один раз после 4 секунд. Комментарий кластера не влияет на сценарий снятия инженеров.

### Итог

Счётчики и ошибки видны по каждой площадке в панели операции. `SUCCEEDED` означает отсутствие неуспешных элементов, `PARTIAL` — часть элементов завершилась с ошибкой, `FAILED` — все обработанные элементы завершились ошибкой. После завершения батч получает статус `COMPLETE`, даже если часть строк не прошла. Уже выполненные назначения и отправленные сообщения не откатываются. История хранит исходный файл/тип работ/шаблон и связь с батчем.

## 3. Массовое снятие инженера с площадок по XLSX

### Подготовка и предпросмотр

1. Снятие выбирается для строк загруженного XLSX (обычно того же плана назначений). Вызов предпросмотра: `POST /api/imports/:id/removal-preview` с уникальными номерами строк.
2. Батч должен существовать; строки должны относиться именно к нему, иметь статус `READY` и содержать площадку, имя/ID инженера и ID задачи. Дубликаты площадки в выбранном наборе запрещены.
3. API заново загружает пользователей и активный план. Сверяет инженера с актуальным пользователем YouGile по нормализованному имени, перечитывает задачу и сверяет её колонку и номер площадки.
4. Предпросмотр показывает целевого инженера, текущий список ответственных, будет ли фактическое снятие (`willRemove`), и кто останется назначенным.

### Подтверждение и выполнение

1. После явного подтверждения `POST /api/imports/:id/remove` снова вызывает подготовку и проверку — результат предыдущего предпросмотра не используется как актуальное состояние.
2. Создаются операция типа `REMOVE` и элементы с `sortOrder`, целевым YouGile user ID и снимком текущего состояния. Операция ставится в очередь `remove-engineers`; ответ `202` возвращает её ID.
3. Воркер читает каждую задачу из YouGile заново, проверяет активный план и номер. Из текущего списка `assigned` удаляет только ID целевого инженера, сохраняя остальных.
4. PUT отправляет оба поля: обновлённый `assigned` и `completed: false`. Это намеренно сбрасывает статус работы в «не выполнена», как в исходном n8n-сценарии.
5. Если инженер к моменту выполнения уже отсутствует, элемент получает `SKIPPED` (повторное снятие не требуется). После успешного PUT — пауза 4 секунды перед следующей площадкой. HTTP 429 повторяется с ожиданием 60 секунд, максимум 10 повторов.
6. Если PUT завершился таймаутом, сервер перечитывает задачу. Если инженер уже отсутствует, считает снятие успешным; если остался — фиксирует ошибку. Это снижает риск ошибочно сообщить о неудаче, когда YouGile применил изменение, но ответ потерялся.

### Итог и ограничения

Операция завершается как `SUCCEEDED`, `PARTIAL` или `FAILED`; подробная ошибка есть у элемента. Снятие не отправляет комментарии, в том числе комментарий кластера. Изменения до ошибки не откатываются. Аварийный максимум — 2 000 строк за запуск.

## 4. Проверить работы

### Назначение

Проверить комментарии по выбранным строкам XLSX, чтобы выяснить, есть ли в чате каждой площадки свежий комментарий о выполнении работ. Этот сценарий читает чаты и не меняет назначения или сообщения.

### Последовательность

1. Оператор выбирает строки и запускает `POST /api/imports/:id/work-check`. Запрос синхронный; браузер одновременно опрашивает `GET /api/imports/work-check/progress?checkId=...` для отображения живого прогресса и оценки оставшегося времени.
2. API проверяет существование батча и принадлежность ему каждой выбранной строки. У строк без сопоставленной YouGile-задачи результат будет «Площадка не найдена в YouGile»; уникальные task ID читаются один раз даже при повторе ID в строках.
3. Период чтения берётся из `AppSetting` `work-check:window-hours`: по умолчанию 48 часов, границы настройки 1–720 часов. Настроить его может ADMIN через конфигурацию портала. Одна и та же временная граница `since` применяется ко всем площадкам в запуске.
4. Чаты читаются строго последовательно. Запрос использует `since` и обычно ограничивается одной страницей по 100 сообщений; если сообщений в окне больше, страницы читаются дальше (до защитного предела). Из текстовых сообщений выбирается наиболее позднее по timestamp; содержимое HTML очищается до текста.
5. Если чтение чата не удалось, выполняется один повтор через 5 секунд. Если повтор не удался, площадка получает ошибку, а обработка продолжается. Для каждого чата выдерживается пауза 4 секунды. Поэтому типичная длительность — около 4 секунд на уникальную площадку плюс время запросов и возможных повторов.
6. После завершения создаётся операция `WORK_CHECK` с результатом каждой строки: найденный комментарий/время, отсутствие комментариев за окно или ошибка чтения. Проверка работ не ставится в BullMQ, но отображается среди активных действий на время выполнения.

### Результаты и особенности

- Комментарий старше выбранного окна не попадёт в результат; сообщение «комментариев за период нет» не означает, что чат пуст за всё время.
- Нет комментария в доступном окне — это пропуск (`SKIPPED`), а не ошибка операции.
- Недоступный чат/ошибка YouGile — `FAILED` для строки; итог может быть `PARTIAL`.
- Результат проверки доступен по операции ограниченное время: после 10 минут завершённая проверка отдаёт `410`. Последние завершённые операции также показываются в течение 10 минут.
- Прогресс хранится в памяти API и после перезапуска процесса не восстанавливается. Сам факт и результат завершённой проверки записываются в БД/историю.
- Подозрительное окончание чтения чата (например, полная страница, где были только вложения, либо достижение лимита страниц) отмечается в журналах для диагностики; результат может не содержать более поздний комментарий, если API вернул необычную пагинацию.

## 5. Написать комментарий

### Подготовка и предпросмотр

1. Оператор выбирает площадки из активного плана, вводит текст либо вставляет сохранённый шаблон и запускает проверку. Технический максимум — 2 000 площадок; длина комментария — от 1 до 10 000 символов после trim.
2. `POST /api/comments/preview` получает уникальные task ID, текст и необязательный тип сохранённого шаблона. Сервер перечитывает активный план и пользователей; задача должна по-прежнему быть в плане. Задачи читаются параллельно ограниченными группами по пять.
3. Предпросмотр показывает номер и название площадки, текущих ответственных и последнее сообщение чата с датой. Чтение последнего комментария даёт контекст и не меняет чат. Если чат нельзя прочитать, отображается ошибка последнего сообщения, но предпросмотр не блокируется: запись комментария может быть разрешена отдельно.
4. Переменные `${data}` и `${time}` здесь автоматически не заменяются (это поведение назначения по XLSX); введённый текст нужно проверить вручную. Разметка `**слово**` при отправке преобразуется в HTML, а поле `text` сохраняет обычный текст.

### Отправка

1. После подтверждения `POST /api/comments` снова выполняет полный предпросмотр и валидацию задач непосредственно перед постановкой в очередь.
2. Сервер создаёт операцию `COMMENT` с автором, текстом и упорядоченными площадками. `post-comments` получает задачу; интерфейс получает `202` и показывает ход операции.
3. Воркер последовательно перечитывает задачу и проверяет, что она ещё находится в активном плане с тем же номером, затем отправляет комментарий в чат задачи. Для каждого успешного комментария выдерживается 4 секунды перед следующей площадкой.
4. Для комментариев не включён автоматический повтор при HTTP 429. При таймауте отправки выполняется проверка чата на наличие того же текста в свежем окне (до двух попыток чтения с ожиданием 2 и затем 3 секунды). Если сообщение найдено, оно считается доставленным; повторный POST не делается, чтобы не создать дубль.
5. По каждой площадке фиксируется успех или ошибка доступа/чата/HTTP. В конце операция получает `SUCCEEDED`, `PARTIAL` либо `FAILED`; текст и сбойные площадки видны в ходе и истории операций.

### Ограничения

- Комментарии отправляются только в активные задачи плана, а не произвольные задачи или столбцы АВР.
- Отправка не меняет список ответственных.
- Уже отправленные комментарии не удаляются, если следующая площадка завершилась ошибкой; автоматического отката нет.
- Ошибка чтения последнего сообщения не равна запрету отправки: это лишь отсутствие контекста в предпросмотре.

## Ключевые маршруты

| Сценарий | Предпросмотр/подготовка | Запуск/проверка | Статус |
|---|---|---|---|
| Точечное назначение | `POST /api/assignments/preview` | `POST /api/assignments` | `GET /api/operations/:id` |
| Массовое назначение XLSX | `POST /api/imports/preview`, `POST /api/imports/:id/assignment-preview` | `POST /api/imports/:id/assign` | `GET /api/operations/:id` |
| Массовое снятие XLSX | `POST /api/imports/:id/removal-preview` | `POST /api/imports/:id/remove` | `GET /api/operations/:id` |
| Проверка работ | выбор строк импортированного XLSX | `POST /api/imports/:id/work-check`; прогресс `GET /api/imports/work-check/progress` | ответ POST и `GET /api/operations/:id` |
| Комментарий | `POST /api/comments/preview` | `POST /api/comments` | `GET /api/operations/:id` |

Для точных контрактов запросов и кодов ответов см. соответствующие обработчики маршрутов в `apps/api/src/modules/assignments/routes.ts`, `apps/api/src/modules/imports/routes.ts` и `apps/api/src/modules/comments/routes.ts`.
